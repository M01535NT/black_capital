# Permisos y operaciones — validación aislada

Se usaron PostgreSQL, Auth, PostgREST y Storage locales reales con estructura contrastada, usuarios sintéticos y cookies SSR reales. No se hicieron escrituras en el proyecto alojado.

## Defectos corregidos en aplicación

- El contador de leads filtraba por estado pero no por agente.
- La creación de tareas aceptaba IDs de asignación ajenos enviados por un agente.
- El límite del proxy truncaba multipart alrededor del límite de archivo; se permite overhead y se devuelve 400 para cuerpos inválidos o excesivos.
- El formulario público enviaba `downloaded_at: null`, incompatible con el NOT NULL/default remoto. Se deja actuar el default confirmado y la entrega documental conserva su registro autorizado. Esta columna heredada no demuestra por sí sola una descarga; una futura migración de semántica/nullable requiere decisión independiente.

## Migración de Storage pendiente de producción

`supabase/migrations/20261016205400_restrict_private_document_storage.sql` elimina los permisos directos amplios del bucket privado y añade una restricción para anon/authenticated. El cliente privilegiado del servidor y la entrega firmada siguen funcionando en las pruebas.

Solo se aplicó al stack local. Producción conserva sus políticas anteriores hasta que se autorice y ejecute una liberación de datos separada. La prueba original falló por acceso permitido y pasó tras el cambio; no confundir el resultado local con una corrección remota ya aplicada.

Antes de aplicar en remoto, volver a capturar sus políticas y verificar consumidores externos que dependan de acceso autenticado directo. Recuperación: mantener ese snapshot y preferir una corrección hacia adelante; no restaurar permisos amplios automáticamente.
